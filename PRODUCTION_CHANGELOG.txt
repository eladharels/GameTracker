  2026-07-27 — BREAKING API CHANGE affecting GameTracker-mobile (Android)
                Admin user endpoints no longer expose or accept notification targets
================================================================================
Security fix. A user's notification target — which device a release reminder
reaches — is their own setting, changed by them on My Account. The admin user
endpoints both returned and accepted those values for OTHER users.

The read was a disclosure: GET /api/users handed every administrator the ntfy
topic and Gotify application token of every user. Both are bearer secrets —
possession of a Gotify app token is enough to post notifications to that user's
devices.

The write was worse, and there were two of them. An admin could overwrite another
user's ntfy_topic/gotify_token via PUT /api/users/:id, or plant them at account
creation via POST /api/users, silently redirecting that user's notifications to a
channel the admin controls. The creation case survives the new user changing their
password, so it outlives them taking full ownership of the account. It is not
invisible — My Account renders both values in plain inputs, so a user who opens
that page can see them — but nothing announces the change.

  GET /api/users
    REMOVED : ntfy_topic, gotify_token   (from every user object in the array)
    UNCHANGED: id, username, can_manage_users, email, created_at, origin,
               display_name, shares_library

  PUT /api/users/:id
    CHANGED : now 400s if the body contains ntfy_url, ntfy_topic, gotify_url,
              gotify_token or telegram_chat_id. Previously the first two were
              written and the other three silently ignored.

  POST /api/users
    CHANGED : same five fields now 400. Previously ntfy_topic and gotify_token
              were written into the new row.

  NOT AFFECTED: GET /api/user/me and PUT /api/user/me/settings. A user reads and
              writes their OWN notification settings exactly as before. This
              change removes only the ability to do it to SOMEONE ELSE.

REMEDIATION for any admin client (this is the realistic break):
  A read-modify-write against the UPDATED server is fine: GET /api/users no longer
  returns the five fields, so PUTting the returned object straight back contains
  only the eight safe columns and does not 400.

  It breaks when the object did not come from this server's current response — a
  client holding a cached user object, one reconstructed from its own model, or a
  form that posts every field it knows about. Those now 400 on the first of the
  five they include.

  Send only the fields you intend to change. The web SPA already does this: its
  admin panel only ever sends {password} or {can_manage_users}, verified at
  frontend/src/App.jsx:416 and :649.

  If the Android admin screen displays a user's ntfy topic or Gotify token, those
  fields will now render empty. That is intended.

WHY THIS SHIPPED AGAINST A FROZEN v1: /api is frozen and permanently supported,
but freezing an API does not freeze a credential leak into it. Recorded here
rather than only in a commit message because GameTracker-mobile talks to this same
REST API and is not in this repository — nobody working on it can see the fix.

The three fields that were previously ignored rather than written (ntfy_url,
gotify_url, telegram_chat_id) are now refused for the same reason the other two
are: an admin tool told {success:true} for a write that did not happen has been
told something false. The two server URLs matter as much as the secrets, since
writing a URL redirects the channel just as effectively as writing the token
presented to it.

  2026-07-27 — API CHANGE affecting GameTracker-mobile (Android)
================================================================================
POST /api/admin/check-releases changed response shape when the release sweep was
extracted into services/jobs.js. The web SPA does not call this endpoint at all
(grepped), but the Android client talks to the same REST API, so this is recorded
here rather than only in a commit message.

  REMOVED : results.totalUsers
  ADDED   : errors[]  — [{ username, gameName?, error }], fixed strings only
  CHANGED : notificationsSent[] now lists release REMINDERS, not the release
            notifications sent for games promoted in the same run. A promote-only
            run therefore returns notificationsSent: [] where it previously
            listed the promoted games.
  UNCHANGED: success, message, updatedGames[]

Why: the sweep existed in four copies (this route, the 08:00 cron,
run_notifications.js, and the reminder logic inside the cron) which had drifted —
most importantly, this route did NOT lowercase the username in its UPDATE, so for
any non-lowercase caller it matched no rows and still reported the game as
updated. All four now call one function.

--- APPLIED 2026-07-29 (Statistics: the status-event log and its three readers) ---
Summary: Records WHEN a status changed, which nothing ever has, and adds a Statistics
         page over it. Also fixes a live bug that was destroying the very history the
         feature counts.

FIRST, THE LIVE BUG (fixed here, would have existed regardless):
  • applyRefreshedMetadata called statusForDate, which returns 'unreleased' for any
    future date REGARDLESS of the current status. A provider moving a release date
    forward — a delay, a re-release, a bad record — demoted a game the user had marked
    `done` to `unreleased`, and the next 08:00 sweep promoted it to `wishlist`. The
    `done` was gone and unrecoverable. A statistics page built on top of that would
    have reported a finished-game count going DOWN.

SCHEMA:
  • migrations/005_status_events.sql — user_game_status_events(user_id, game_id,
    from_status, to_status, changed_at TIMESTAMPTZ, source). Applied automatically at
    boot by schema-migrate.js; no operator step.
  • ON DELETE CASCADE from users, but deliberately NO foreign key to user_games: a
    composite FK would cascade history away when a game is removed, and "I finished 12
    games this year" must not become 11 because one was tidied up.
  • DELIBERATELY NOT SEEDED. There is no honest changed_at for pre-existing rows, so
    the table starts EMPTY and the page states its own coverage. Same rule as 004. A
    library with 48 finished games therefore reports 0 completions on day one — that is
    correct, not a fault, and the page says so rather than drawing a zero.
  • `source` (user / release_sweep / metadata_refresh / backfill) is the column the
    feature rests on. Every achievement query filters source = 'user'. The 08:00 sweep
    promotes unreleased -> wishlist when a date passes and nobody did anything; one
    library here has 58 unreleased games, so a single nightly run would otherwise post
    the largest number on the page.
  • Written in ONE place, library.js#recordStatusEvent, called by all five status write
    paths, inside the caller's transaction so the event and the write commit together.

WHAT CHANGED:
  • services/stats.js — the event log's answers only: completions and playing->done
    durations, plus a `coverage` block including `truncated`. Deliberately returns
    nothing the library response already carries.
  • GET /api/user/:username/stats — v1, auth + owner-or-admin, a thin adapter over the
    service. On v1 because its only client is the SPA, which holds a session JWT and
    therefore cannot call /api/v2 at all. Third and last documented exception to the
    freeze; see CLAUDE.md for the three conditions.
  • GET /api/v2/stats/summary — the token-scoped twin over the same service, aggregated
    so an agent does not spend its context on a row per completion.
  • MCP tool `get_statistics` (16 tools now, was 15).
  • frontend/src/StatsPage.jsx + dateUtils.js — hand-rolled CSS/SVG charts (the six
    accent presets mutate --color-accent at RUNTIME and a canvas chart cannot inherit
    that). Bucketing is client-side: date_trunc would bucket in the SERVER's timezone.
  • A failed load renders the error and NOTHING else — no chips reading 0. Same class of
    failure as the empty-library incident: a confident zero is indistinguishable from a
    real one.
  • Library write rate limit — 240 writes per 5 minutes per user id, on the v1 add/status
    route and the two v2 library writers.
  • CI: test/integration/stats.test.js and status-events.test.js run inside the backend
    container during the smoke stage, against a real Postgres. Stubbing db.promises
    cannot prove the five write paths land rows with the right `source`, and a
    regression there is PERMANENTLY destructive — unrecorded history cannot be
    backfilled.

--- APPLIED 2026-07-28 (MCP server — a fourth container) ---
Summary: Exposes a narrow, task-shaped subset of /api/v2 over the Model Context
         Protocol so an AI assistant can work with a library. Separate npm package,
         separate image, separate container.

WHAT CHANGED:
  • mcp/ — 16 tools shaped around what people ask for rather than one per endpoint.
    DELIBERATELY EXCLUDES user management, settings, token administration and
    instance-wide jobs, even when handed an admin-scoped token. The inventory is PINNED
    in mcp/test/tools.test.js the way route tiers are.
  • HOLDS NO CREDENTIALS. No token in its environment or config; every request must
    carry its own Bearer PAT, forwarded unchanged. Authorization stays the backend's and
    reaching the port grants nothing. Stateless — a fresh McpServer per request.
  • Published on 127.0.0.1:3001 by default. Runs read_only with no volumes, no database
    and no secrets, because it needs none of them.
  • Runs node:22-slim and REQUIRES >=20: the SDK's HTTP transport calls the GLOBAL
    crypto.randomUUID(), and globalThis.crypto is only exposed from Node 19. On
    node:18-slim /health answered 200 while EVERY MCP call returned -32700 for a full
    deploy cycle. The smoke stage now asserts a real `initialize` RESULT rather than
    HTTP 200 — a JSON-RPC error is delivered with a 200, so a status check proves
    nothing.
  • CI: trivy-mcp added; deploy now gates on 8 upstream jobs.
  >>> OPERATOR NOTE (only if a client runs on another machine):
      Set MCP_BIND to the LAN address it should answer on. For a CI deploy that must be
      a repository VARIABLE (Settings -> Secrets and variables -> Actions -> Variables);
      a .env on the host is NOT read by the deploy job, which checks out into a fresh
      workspace, and ${MCP_BIND:-127.0.0.1} then quietly falls back to loopback. The
      token crosses the network in a cleartext header — put TLS in front of anything
      that is not a trusted LAN. See SECURITY_HARDENING_2026-07.md section 11.

--- APPLIED 2026-07-28 (API tokens in the browser, and admin revocation) ---
Summary: Completes the token story for humans: My Account -> API Tokens, a browsable
         API Reference page, and a way for an admin to revoke someone else's tokens
         without deleting their account.

WHAT CHANGED:
  • GET/POST /api/user/me/tokens and DELETE /api/user/me/tokens/:tokenId — session
    authenticated, operating on req.user.id only. THE BOOTSTRAP, and the second
    exception to the v1 freeze: /api/v2 takes tokens only, so the endpoint that mints
    your FIRST token cannot itself require one.
  • SUDO MODE on minting: the password is re-checked, because a token outlives the
    12-hour session that created it. Local accounts verify with bcrypt, directory
    accounts with a real LDAP bind through the SAME function the login route uses.
    ldap.requiredGroup is re-checked here — it is the one authorization signal that
    lives in the directory and is never mirrored into `users`, so without the re-check a
    deprovisioned account turns its residual session into a token no admin can see.
    Rate limited per user id in its own key namespace, plus a second budget (20 per 2
    minutes) covering every attempt that reaches the directory. A directory FAULT
    answers 503, never "incorrect password" — you cannot fix an outage by retyping.
  • KNOWN AND ACCEPTED: this does not constrain a stolen ADMIN session. An admin can
    reset their own password through PUT /api/users/:id without the old one and then
    mint. Closing it means adding a required field to a frozen v1 route, so it is
    recorded rather than done quietly.
  • GET/DELETE /api/v2/users/:id/tokens (+ /:tokenId) — admin revocation. Blocking new
    mints is not revoking old ones: a token minted before its holder lost
    ldap.requiredGroup keeps working, and destroying it used to mean deleting the
    account and its library. The bulk delete answers 200 with a COUNT, not 204 — zero
    revoked is a success, and a 204 could not tell "revoked seven" from "revoked none".
    A user id that does not exist is a 404, never {"revoked": 0}.
  • API Reference page (frontend/src/ApiDocsPage.jsx) — Swagger UI over GET /api/openapi/v2,
    so the SPA renders the same contract CI validates. VENDORED, not CDN-loaded:
    frontend/nginx.conf sets script-src 'self'.

--- APPLIED 2026-07-27 (/api/v2 goes live: contract, tokens, and the drift gate) ---
Summary: A second API surface for scripts and agents, specified before it was written.
         v1 is unchanged and stays frozen and supported — the Android app is a build we
         do not control.

WHAT CHANGED:
  • migrations/003_api_tokens.sql — personal access tokens. Opaque gt_pat_<base64url>,
    SHA-256 hashed, so a database dump yields no working credentials. Two scopes,
    library and admin, and a scope may only ever NARROW the privilege read from `users`:
    a library-scoped token held by an admin is not an admin, and an admin-scoped token
    held by a non-admin does not become one.
  • migrations/004_user_games_added_at.sql — added_at, nullable and deliberately NOT
    backfilled. NULL means "unknown", not "old"; ordered reads must say NULLS LAST.
  • v1's authRequired now accepts a PAT alongside a JWT. ADDITIVE — a new credential
    type, not a shape change, so no route or response shape moved. The login rate
    limiter lives inside the login route, so token auth never reaches it: 5 retries from
    a script would otherwise lock the owner out for 15 minutes.
  • /api/v2 — 35 operations, PAT-ONLY. It refuses a session JWT deliberately: a JWT
    carries no scope, so accepting one would make the admin boundary bypassable by
    logging in with a password. Errors are RFC 9457 problem+json with a stable code;
    mutations return the resource or 204; a DELETE of something absent is a 404, not
    {"success":true}; long sweeps return 202 and a job to poll.
  • openapi/gametracker-v2.yaml is the SOURCE for the routes, not a description of them.
    CI fails if an operation marked x-implemented has no route, or a v2 route is not
    such an operation, or its x-required-scope disagrees with the router-derived tier.
  • GET /api/capabilities (auth tier) — version discovery. Added to v1 BEFORE the freeze
    bit, because after it a client has no way to learn v2 exists.
  • Build toolchain dropped from the backend image; sqlite3 became a devDependency, used
    only by the spent one-shot migration script. That was hundreds of megabytes fetched
    on every build, and had already failed one with "You don't have enough free space in
    /var/cache/apt/archives/" on the self-hosted runner. Adding a native dependency
    reinstates all of it.
  • test/api-surface.test.js now walks the live router across mounted routers and
    asserts the tier of all 83 routes. An earlier version credited middleware by router
    membership rather than stack position and reported an UNAUTHENTICATED route as
    authenticated — it failed in the safe-looking direction, which is the single failure
    mode that file exists to eliminate.

WHAT CHANGED:
  • New dedicated Postgres service in both compose files:
      production  -> container_name postgres-gametracker, named volume gametracker-pgdata
      CI smoke    -> container_name postgres-gametracker-smoke, no volume at all
    The port is NOT published in either. The backend is gated on service_healthy.
    This is GameTracker's own database — it does not touch the unrelated Postgres
    instances on this host (the other app's postgres:16-alpine, or Guacamole's 15.2).
  • db.js — pg connection pool plus a run/get/all shim matching node-sqlite3's callback
    surface, so the ~65 existing call sites port without being rewritten.
  • schema-migrate.js + migrations/*.sql — ordered, transactional migrations tracked in
    a schema_migrations table. ANY failure is fatal. This replaces initializeSchema(),
    whose swallowed errors shipped fresh installs missing four columns.
  • scripts/migrate-sqlite-to-postgres.js — the one-shot data migration. MANUAL, never at
    boot, and SINGLE-SHOT rather than idempotent: an aborted run rolls back completely and
    can be re-run, but a COMPLETED run refuses to run again (exit 5) because the target is
    no longer empty. --dry-run performs the entire load and then rolls it back, so
    constraint and type failures surface during the rehearsal, not mid-cutover.
  • backend now runs with read_only: true. SQLite's need for a writable /app was the
    only thing blocking it.

BEHAVIOUR CHANGE — DELETING A USER NOW DESTROYS THEIR LIBRARY:
  ON DELETE CASCADE was added to user_games.user_id and both user_shares columns. SQLite
  DECLARED these foreign keys but ran with PRAGMA foreign_keys OFF, so they never fired —
  which is exactly how the 30 orphaned user_games rows accumulated.
  This is not purely a safety fix. Previously, DELETE /api/users/:id left the user's whole
  library behind in the table, theoretically recoverable by recreating the account at the
  same id. It is now deleted with them, permanently. There is exactly one such delete path,
  it is admin-only, root cannot be deleted, and the frontend confirms first — but the
  operator should know the semantics changed.

SCHEMA DECISIONS:
  • user_games.game_id is TEXT, not INTEGER. The SQLite column was DECLARED INTEGER but
    every one of the 379 production rows holds a string like 'igdb_19564'. Postgres would
    have rejected every insert. This was verified against the live database, not assumed.
  • Booleans stay INTEGER (0/1) and dates stay TEXT. Both are load-bearing across the
    backend, the frontend AND the Android client. Converting them is a behaviour change
    and belongs in its own commit.
  • can_create_users is preserved: unused by the backend but read by frontend App.jsx:181,
    and root has it set in production.

DATA PROBLEMS FOUND IN PRODUCTION (Postgres will enforce what SQLite ignored):
  • 30 user_games rows reference user_id 2, 3, 4, 5 or 8 — none of which exist any more
    (19 of them belong to the missing user 5). The migration HALTS on these by default
    and requires an explicit operator decision. It will not delete data on your behalf.
  • 2 user_shares rows point at 'Orelsh' where the user row is 'orelsh'. This is a case
    mismatch, not a dead user, and is repaired automatically.
  • No ghost users found: every NULL-password account has origin='ldap', which is correct.

>>> CUTOVER PROCEDURE (operator runs this):
  1. BACK UP FIRST. There is no existing backup story.
       cp /home/docker/gametracker/data/gametracker.db  ~/gametracker.db.$(date +%F)
       cp /home/docker/gametracker/data/settings.json   ~/settings.json.$(date +%F)
       cp /home/docker/gametracker/data/sent_notifications.json ~/sent.json.$(date +%F)
  2. Add POSTGRES_PASSWORD to the repository's GitHub Actions secrets, and to
     /srv/actions-runner/_work/GameTracker/GameTracker/.env if you deploy by hand.
     Generate with: openssl rand -base64 32
  3. Merge -> CI deploys -> postgres-gametracker comes up empty and the backend
     applies migrations/001_initial_schema.sql automatically.
  3.5 IMMEDIATELY stop the backend and frontend — before anyone can reach them.
     CI leaves the stack RUNNING against an empty database. In that window an LDAP
     user logging in is auto-provisioned, which makes the target non-empty and NOT
     bootstrap-root-only, so step 6 refuses with exit 5 and the only way forward is
     destroying the volume. Real users would also see an empty library and may
     re-add games. Do not rely on the script's refusal to save you here.

  4. Confirm the backend is stopped, keeping the database running:
       docker compose -f docker-compose.yaml stop backend
     >>> IMPORTANT: by this point the backend has already booted once and created
         a BOOTSTRAP `root` account with a randomly generated password (printed in
         its logs). That row occupies id=1 and would collide with the real root
         row from SQLite. Step 6 handles this explicitly; do not skip the flag.
  5. Dry run the migration and READ THE REPORT:
       docker compose -f docker-compose.yaml run --rm --no-deps \
         -v /home/docker/gametracker/data/gametracker.db:/legacy.db:ro backend \
         node scripts/migrate-sqlite-to-postgres.js --sqlite /legacy.db --dry-run
     Expected outcomes, both normal:
       exit 5 — "TARGET DATABASE IS NOT EMPTY" because of the bootstrap root row.
       exit 3 — halted on the 30 orphaned user_games rows.
     The script refuses to load into a non-empty database. That refusal is the
     safety net: loading on top of the bootstrap row would silently DISCARD the
     real root account's password hash and permissions while still reporting OK.
  6. Run the load, replacing the bootstrap root and quarantining the orphans:
       docker compose -f docker-compose.yaml run --rm --no-deps \
         -v /home/docker/gametracker/data/gametracker.db:/legacy.db:ro backend \
         node scripts/migrate-sqlite-to-postgres.js --sqlite /legacy.db \
           --allow-orphans=quarantine --replace-bootstrap-root
     The VERIFICATION table must read OK on all three rows, in BOTH the
     "expected" and "inserted" columns. An "inserted" count lower than "expected"
     means rows were skipped rather than loaded — stop and investigate.
  7. docker compose -f docker-compose.yaml start backend
  8. Verify by hand: log in as root with the ORIGINAL production password (not
     the generated one from step 3 — it belonged to the bootstrap row, which the
     migration removed), view the library, open notification settings, check sharing.
  9. Leave the SQLite file untouched for at least a week. It is the rollback.

>>> ROLLBACK (if the deploy goes wrong):
  The SQLite file is never written to by the migration, so rollback is just
  redeploying the previous image:
    git revert <merge commit>   # or: git checkout <previous main sha>
    docker compose -f docker-compose.yaml down
    docker compose -f docker-compose.yaml up -d
  The old code reads /home/docker/gametracker/data/gametracker.db exactly as before.
  Note the pre-Postgres compose does not mount gametracker.db any more, so a revert
  must restore the OLD docker-compose.yaml too — reverting the whole merge does this.
  Leave the gametracker-pgdata volume in place; it costs nothing and preserves the
  migrated state for a second attempt.

  *** ROLLING BACK DISCARDS EVERY WRITE MADE SINCE CUTOVER. *** The SQLite file is
  a snapshot frozen at step 6. Any game added, status changed, backlog reordered or
  account setting saved against Postgres is LOST on rollback and cannot be merged
  back. This is why the rollback window matters: the longer the app runs on
  Postgres, the more expensive reverting becomes. Tell users nothing is durable
  until you have committed to the migration, and prefer fixing forward once real
  traffic has landed.

>>> ROTATING POSTGRES_PASSWORD (read before you try):
  POSTGRES_PASSWORD is only consumed by the image's FIRST-RUN initdb. After that
  the role's password lives inside the gametracker-pgdata volume. Changing the
  GitHub Actions secret therefore changes what the BACKEND presents, but NOT what
  the SERVER expects — the backend then fails authentication on every boot.
  To rotate, change it in BOTH places:
    docker exec -it postgres-gametracker \
      psql -U gametracker -d gametracker \
      -c "ALTER ROLE gametracker WITH PASSWORD 'new-secret-here';"
    # then update the Actions secret and redeploy

>>> BACKUP / RESTORE (new — none previously existed):
  Backup (safe while running):
    docker exec postgres-gametracker pg_dump -U gametracker -Fc gametracker \
      > ~/gametracker-$(date +%F).dump
  Restore into an empty database:
    docker exec -i postgres-gametracker pg_restore -U gametracker -d gametracker \
      --clean --if-exists < ~/gametracker-YYYY-MM-DD.dump
  Suggested cron (daily 02:00, keep 14 days) — add to the operator's crontab.
  Create the directory first: mkdir -p /home/docker/gametracker/backups
  Dump to a temp file and only publish it if pg_dump SUCCEEDED and produced bytes.
  A naive `pg_dump > file` leaves a zero-byte file behind on failure — a
  dump-shaped object that is not a backup, and that the retention rule then keeps:
    0 2 * * * D=/home/docker/gametracker/backups; T=$D/.tmp-$$.dump; \
      docker exec postgres-gametracker pg_dump -U gametracker -Fc gametracker > $T \
      && [ -s $T ] && mv $T $D/gt-$(date +\%F).dump \
      && find $D -name 'gt-*.dump' -mtime +14 -delete; rm -f $T
  Verify a dump is restorable at least once — an untested backup is not a backup:
    docker exec -i postgres-gametracker pg_restore -l < ~/gametracker-YYYY-MM-DD.dump
  NOTE: `docker compose down --volumes` DELETES gametracker-pgdata. The deploy job
  never passes --volumes; do not add it.

  a 65-call-site engine swap, in a codebase with no test suite, is how you get an outage
